# 2026-09-16 评审复核与修复记录

核对对象：`code-review-2026-09-16.md` 及本次开始时的工作区代码。原报告保留不改。本次是在已有未提交修改上修复，没有执行部署或真实 PM2/Caddy 停启。

## 结论

报告发现了需要修复的真实问题，但两项 P0 的定级、部分故障描述和部分修复建议不够准确。目前没有证据证明已经发生数据损坏、必然写丢失或系统级紧急事故。维护调度、停止顺序和引用附件权限应在发布前修复。

| 项目 | 核实结果及建议级别 | 已采取的修改 |
| --- | --- | --- |
| 1. CLI 派生轮询进程 | 成立，建议 P1。每次调用都会派生进程；有预告时会反复睡眠和读状态，直到取消或激活。这些是存活的后台进程，不是操作系统意义的 zombie；CPU 惊群和内存压力取决于调用次数，不能直接认定 P0。 | 从公共入口移除派生逻辑。在服务 `load()` 启动、且状态为 scheduled 时，才派生最长 30 秒的一次性修复命令。修复命令持操作锁并重新检查状态，仅在 PM2 调度器不在线时恢复它；长期轮询仍由 PM2 管理。CLI、help、inactive/active 状态不会创建轮询进程。 |
| 2. 停机顺序 | 成立，建议 P1。原代码先停 MongoDB，再停上层服务。在途请求或任务可能失败；但 active 标记先于停止操作写入，新 HTTP 请求会进入维护页，并不能据此认定所有请求都会崩溃或 MongoDB 数据必然丢失。 | 按 Hydro → judge → sandbox → MongoDB 停止，按相反顺序恢复，保留维护前在线服务的快照和恢复健康检查。 |
| 3. 引用题目公开附件 | 成立，建议 P1。源域测试数据权限错误地同时控制了公开附件。报告之外，批量下载入口也存在同样限制。 | 修复详情页、单文件下载、批量下载及 problem API。公开附件沿用目标题目/比赛访问控制；testdata 仍检查源域权限，目标域管理员也不能绕过。 |
| 4. 恢复后调度器残留 | 成立，但建议 P2。PM2 stopped 条目不是占用内存的死进程；即使复活，在 inactive 状态下也会退出。主要是进程列表与持久化快照不整洁。 | active 恢复成功及已经 inactive 的 off 均尝试删除调度器并保存列表；恢复失败仍保留维护状态和快照。 |
| 5. 排他锁竞态 | 部分成立，建议 P2。mkdir 本身是原子的，问题在于 Node 端将 owner 尚不存在误判为可以回收。Shell 原本不会在 owner 缺失时删除目录，因此报告不能原样套用于两者。两者原有的自动回收陈旧锁也存在多个回收者并发的风险。 | 两个入口统一拒绝自动删除已有锁，避免初始化窗口和并发回收竞态。异常退出后遗留的锁需人工核实后清理，已补充运维文档。单纯 sleep 100ms 或把目录换成 wx 文件，并不能彻底解决“创建后发布 PID”与自动回收的竞态。 |
| 6. 横幅遮挡导航 | 成立，建议 P2。导航本身也是 fixed，仅把横幅改成 sticky 或给 body 加 padding 并不足够。 | 横幅进入文档流并 sticky；ResizeObserver 跟踪真实高度，同步偏移固定导航、阴影及移动菜单，并调整移动菜单最小高度。取消公告后解除观察并清除偏移。 |
| 7. Service Worker | 成立：缓存行为建议 P2，声明顺序属于 P3。缓存规则接受任何末段带点号的 URL，并非专门的 .html 规则；Cache API 不会因为页面 fetch 设置 no-store 就自动拒绝 cache.put。 | 两个维护路径（含查询参数）在 fetch 入口直接放行，跳过缓存及镜像域名重写，同时从预缓存候选排除。将配置初始化函数移到使用之前。 |
