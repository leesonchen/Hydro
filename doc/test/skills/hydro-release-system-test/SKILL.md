# Hydro release system test

Use this skill when asked to assess changes between two Hydro deployments and produce a release note plus browser-tested evidence. Locate the Hydro repository root before using the relative script paths. Inputs are the two deployment identities (prefer active package/version snapshots), the reachable Hydro environment for the target release, and any known test-account label or scenario constraints. Save the release note, case results, and evidence under `doc/test/` using the repository's report conventions.

1. Compare the deployed package sets and versions with `doc/test/scripts/compare-releases.cjs`. Base the change inventory on the packages actually active in each deployment; date-filtered `git log` alone can miss deployment differences. Turn each user-visible change into one or more concrete browser scenarios.
2. Read [references/report-and-coverage.md](references/report-and-coverage.md) for evidence grades, statuses, report fields, and Hydro-specific scenario invariants. Build the matrix before execution, covering changed user-visible behavior and relevant regression paths.
3. Run browser scenarios through `doc/test/scripts/browser-system-test.cjs`, using `--help` for its CLI and a real browser session. `--only ID,ID` limits a focused retest; include its prerequisite cases. Save screenshots or other browser artifacts alongside the report in `doc/test/`. HTTP/API/CLI actions may prepare fixtures and supplement evidence; they cannot substitute for browser interaction where a browser entry point exists. Keep the target release fixed while collecting results; a discovered defect is a report finding, not permission to silently replace the tested release.
4. Report every case as `pass`, `fail`, `blocked`, or `skipped`, with observed behavior, evidence paths, and a concise release note tied to the deployment comparison. Inspect screenshots, page responses, and fixture validity before classifying a failure as a product defect. Driver syntax/protocol failures are blocked; other unclassified failures need triage. Correct driver/fixture errors and retest affected cases with their prerequisites. Mark missing browser access or unavailable prerequisites as blocked; use skipped only for out-of-scope cases and explain why. Descriptions of failures and delivery success must follow the current case results, not fixed report boilerplate.

Use authorized test accounts and data within the session's existing scope. For a localhost run using `testuser.txt`, select the labelled local accounts rather than the production/exam password section; honor a different environment explicitly selected by the user. Never include passwords, session material, or secret-bearing output in notes, commands, screenshots, or reports. Container/package reads and cleanup must stay within the authorized target and owned fixtures. For development releases, follow the repository root `AGENTS.md`; a system test does not authorize publishing or upgrading, and package files must not be copied into a Hydro installation by hand.

Content feedback sends real messages to the domain owner and system administrators. Prepare the exact test text and recipients before seeking any missing message authorization. Reuse authorization already given in the session; `--allow-feedback` enables the runner's delivery/reply case after that authorization. Mask unrelated private conversations in screenshots. Ordinary messaging and feedback replies have different permissions; missing ordinary send permission is a test prerequisite issue, not evidence that feedback replies are broken.

For changes to template saving or classroom copying, also run `node doc/test/scripts/extra-course-test.cjs --out doc/test/releases/<run>/evidence/extra-course --container <target>`. This helper prepares independent fixtures and tests both template saving and two class copies through the browser. Add its planned IDs to the matrix before execution and merge its completed results with links to its original evidence.

Generate the report with `node doc/test/scripts/generate-report.cjs --run doc/test/releases/<run>`. Preserve initial attempts and link final retest evidence rather than erasing failed observations. Merge only completed, selected retest results; do not let skipped cases overwrite existing results. The plan, final results, screenshot links, and feature-to-case mapping must agree.

Keep fixture creation separate from observed browser behavior. Create any login material in a temporary directory and remove it in a `finally` cleanup path. Prefer read-only use of existing exams. Put any write scenarios in a separate temporary domain, track judge jobs to completion before cleanup, and record whether storage is still active or scheduled for `autoDelete` (default retention is seven days).

For changed course datetime flows, run `node doc/test/scripts/course-datetime-test.cjs --out doc/test/releases/<run>/evidence/datetime --container <target>` as well. It tests exact assessment timestamp retention, explicit bound edits, started-test metadata, two browser timezones relative to the profile timezone, and native contest setting submission. It uses browser timezone emulation without changing real account preferences. Add all IDs from its case plan to the matrix and merge completed results with their original evidence links.
